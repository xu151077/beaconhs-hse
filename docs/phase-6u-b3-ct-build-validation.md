## 4. Secret checks

The test key was used as the search value; the key itself was never printed.

| Check                                      | Result                                                      |
| ------------------------------------------ | ----------------------------------------------------------- |
| Build log contains key                     | NO                                                          |
| Image `Config.Env` contains key            | NO                                                          |
| Image history contains key                 | NO                                                          |
| Key present in image filesystem            | YES — Next.js standalone server-reference manifests         |
| Exact locations (without printing content) | `/app/apps/web/.next/server/server-reference-manifest.json` |
|                                            | `/app/apps/web/.next/server/server-reference-manifest.js`   |
| Occurrences                                | 1 in each file, field `encryptionKey`                       |

The image environment contains only non-secret runtime keys:

```text
PATH,NODE_VERSION,YARN_VERSION,NODE_ENV,PUPPETEER_SKIP_DOWNLOAD,
PUPPETEER_EXECUTABLE_PATH,APP_ROLE,HOME
```

The `server-reference-manifest` files are generated by Next.js so the standalone
server can decrypt Server Action closures at runtime. The build key is therefore
inside the image even though it never enters the build log or environment. This
is expected for the current self-contained Next.js image design. It does **not**
satisfy a literal "no key material anywhere in the image" criterion. If that
criterion is mandatory, the application needs a runtime key-injection design;
that would be a separate change and was not made in Phase CT.

Operational consequence: the image must only be stored in a private registry
with restricted pull access. Do not publish it to an untrusted registry and do
not reuse its key outside this deployment line.

## 5. What this proves and what it does not

Proven:

- The current working-tree `Dockerfile` is buildable with BuildKit and a required
  secret.
- The produced image contains the web, worker, scheduler, health, entrypoint and
  Next.js standalone artifacts.
- The scheduler in the built artifact detects a missing repeat registry and
  exits non-zero, then recovers on rerun.
- The secret does not appear in the build log, image environment, or image
  history.

Not proven / not done:

- The image was **not pushed** and **not deployed** to `beaconhs-phase-aj`.
- No production secret was used; only a disposable test key.
- The image's web or worker process was not run against the live test database.
- The "no key material in the image" acceptance criterion is not met because of
  Next.js's runtime manifest; see the warning above.
